# FAISS and Vector Databases

A vector database, or vector index, is a data structure purpose-built for storing large numbers of high-dimensional vectors and quickly finding the ones most similar to a given query vector. This is a different problem from a traditional relational database's exact-match lookups: with millions of 384- or 768-dimensional embeddings, comparing a query against every single vector one at a time (a "brute-force" or "flat" search) becomes slow, so specialized indexing structures and search algorithms are needed.

FAISS (Facebook AI Similarity Search) is an open-source library, developed by Meta AI, that implements a wide range of these similarity-search algorithms and is one of the most common choices for local, offline vector search because it runs entirely in-memory on a single machine with no external server or network call required. FAISS offers several index types with different speed/accuracy/memory trade-offs. The simplest, IndexFlatIP (inner product) or IndexFlatL2 (Euclidean distance), performs an exact brute-force search — guaranteed to find the true nearest neighbors, at the cost of scanning every stored vector, which is perfectly fine for corpora of a few thousand to a few hundred thousand chunks, but becomes a bottleneck at web scale. For much larger collections, FAISS provides approximate-nearest-neighbor structures such as IVF (inverted file index, which first clusters vectors and only searches the most promising clusters) and HNSW (a navigable small-world graph), which trade a small amount of accuracy for large speed gains.

When embeddings are L2-normalized (rescaled to unit length) before being added to the index, an inner-product search is mathematically identical to a cosine-similarity search, which is why many RAG pipelines pair IndexFlatIP with normalized Sentence-BERT embeddings to get a fast, exact cosine-similarity retriever without any extra math at query time.

Because FAISS keeps everything in memory and needs no server process, database credentials, or internet connection, it is well suited to offline and privacy-sensitive RAG deployments: the entire retrieval stack — embedder plus index — can be packaged and run on a single laptop. The trade-off is that a FAISS index alone does not automatically stay in sync with new or deleted documents; an application has to explicitly re-embed and re-add (or rebuild) the index whenever the underlying document store changes, which is exactly why a RAG system's "build index" or "re-index" step is typically a separate, explicit action rather than something that happens automatically in the background.
