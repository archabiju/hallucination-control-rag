# Chunking Strategies for Document Retrieval

Before a document can be retrieved by a RAG system, it has to be broken into smaller pieces, or chunks, because embedding models have a maximum input length and, even below that limit, a very long passage produces a single embedding vector that blends together many unrelated ideas, making it a poor match for any specific query. Chunking is the step that decides how a raw document — a PDF, a Word file, plain text — gets split into the units that will actually be embedded, indexed, and retrieved.

The simplest approach, fixed-size chunking, splits text every N tokens (or words, or characters) regardless of sentence or paragraph boundaries. It is easy to implement and gives predictable chunk sizes, but it can cut a sentence or an idea in half at an arbitrary point, which may separate a claim from the context needed to understand or verify it. To reduce this problem, fixed-size chunking is almost always combined with overlap: instead of starting the next chunk exactly where the previous one ended, the next chunk begins some number of tokens before that boundary, so that content near a cut point appears in full in at least one chunk. A common configuration — 512 tokens per chunk with a 50-token overlap — balances chunk size against redundancy: large enough to preserve context within a chunk, with enough overlap that a boundary falling mid-sentence or mid-idea is still fully captured in a neighboring chunk, at a storage and indexing cost of roughly ten percent extra text.

More content-aware alternatives exist. Sentence- or paragraph-based chunking respects natural language boundaries, so a chunk never ends mid-sentence, at the cost of more variable chunk sizes. Semantic chunking goes further, using embedding similarity between adjacent sentences to decide where topic boundaries actually occur, splitting a document where the subject matter meaningfully shifts rather than at a fixed token count. Recursive or hierarchical chunking splits a document by structure first (sections, then paragraphs, then sentences) and only falls back to a fixed size if a structural unit is still too long.

Chunk size has a direct, measurable effect on retrieval quality. Chunks that are too large dilute the embedding with multiple topics, so a query about one specific fact inside a large chunk may not score highly enough against it to be retrieved, and even if retrieved, the surrounding irrelevant text adds noise to the context the generator receives. Chunks that are too small lose context — a sentence like "this reduces the error rate by half" is uninformative on its own without the preceding sentence identifying what "this" refers to. Choosing a chunking strategy and chunk size is therefore not a minor preprocessing detail but one of the first design decisions that shapes everything downstream in a retrieval-augmented pipeline, including how easy it later is to attribute a generated claim back to a single, coherent source passage.
